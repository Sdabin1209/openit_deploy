# 0001. 오케스트레이션은 단일 서버의 Docker Compose

- 상태: 채택
- 날짜: 2026-10-28

## 맥락

이 시스템은 병원 한 곳의 서버 한 대에 서비스 일곱 개와 PostgreSQL, 정적 화면 둘을 올린다(docs/brief.md: '단일 서버에서 Docker Compose로 시스템을 합치고'). 허용 중단 시간과 복구 시점(O16)은 사용자 결정 전이고, 서버 전체 중단은 비보증이며 서버 밖 감시가 알린다(D10).

## 결정

운영 구성은 `compose.yaml` 하나(이미지는 digest로만 참조, D07), 로컬 레지스트리는 별도 프로젝트(`compose.registry.yaml`), 주기 잡은 호스트의 스케줄러 tick이 `docker compose run`으로 띄운다. 다중 서버·자동 확장은 하지 않는다.

## 왜 (따른 표준과 근거)

- 규모에 맞는 도구를 쓴다: 서버 한 대에서 선언형 파일 하나로 서비스 의존(`depends_on: service_healthy`), 네트워크 분리, 비밀 파일, 자원 한도, 재시작 정책을 모두 표현할 수 있다. 출처: docs/brief.md 1절, docs/design.md 1~2절.
- 되돌리기가 쉽다: 코드 축 롤백은 digest 잠금을 이전 것으로 되돌리고 `up.sh`를 다시 돌리면 끝난다(docs/design.md 2절, E2E가 실제로 돈다).
- 측정한 근거는 없다: 처리량·동시 키오스크 수 한계는 측정한 적이 없다(점검 G1 '확인 못 함'). '한 대로 충분하다'는 가정이지 측정이 아니다.

## 검토한 대안과 버리는 이유

- **Kubernetes**: 서버가 한 대라 스케줄링·자동 확장의 이득이 없고, 운영해 줄 클러스터 전문 인력이 이 프로젝트에 전제되어 있지 않다. 버린다.
- **systemd 유닛 직접 관리**: 컨테이너 의존 순서·네트워크 분리·비밀 마운트를 유닛 파일 여러 개로 흩어 써야 하고 한 파일로 검토하기 어렵다. 점검 호출 주체(check-health, 스케줄러 tick)만 systemd timer 예시로 둔다(config/systemd/).
- **Docker Swarm**: compose 파일을 거의 그대로 쓰지만 이 구성에 필요한 기능이 없고(파일 secrets의 uid/mode 같은 swarm 전용 옵션은 쓸 수 있으나) 새 운영 지식이 든다. 필요가 생기면 재검토.

## 결과

- 한 서버가 죽으면 전부 멈춘다(비보증, D10). 서버 밖 감시(`config/external-monitor.example.yaml`)와 백업이 보완한다.
- 호스트 재부팅 뒤 기동 순서는 `restart: unless-stopped`와 depends_on에 맡긴다(점검 A5: 재부팅 절차를 런북에 명시할 것).

## 되돌리는 조건

서버가 둘 이상 필요해지거나(처리량·가용성 요구가 O16에서 확정) 무중단 배포가 요구되면 Kubernetes 또는 Swarm을 다시 검토한다.
