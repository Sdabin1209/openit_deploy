# 0014. 영역 변경 때는 verify-area(시험 + check-all + 연결된 E2E 단계 --only)로 되먹임을 줄인다

- 상태: 채택(대응표는 정적 추정)
- 날짜: 2026-10-28

## 맥락

전체 E2E는 약 8분(준비 100초, Compose 기동 88초, 단계 1~8 138초, 스케줄러 6초, 백업·복구 96초, 롤백 58초; 마지막 전체 실행의 구간별 소요). 영역 하나를 고칠 때마다 돌리기엔 길고, 안 돌리면 호출 경계의 깨짐을 늦게 안다.

## 결정

`scripts/verify-area.sh <영역>`이 (1) 영역 자체 시험, (2) check-all, (3) 그 영역과 연결된 E2E 단계 묶음(`e2e.sh --only`, 선행 단계 포함)을 돌린다. 영역→단계 대응과 각 대응이 보는 호출 경계(`why`)는 `config/verify-areas.yaml` 한 곳에 있다. 영역 내부만 바뀐 경우 `--no-e2e <이유>`(이유 필수) 또는 바뀐 파일이 전부 문서·시험일 때 'E2E 필요 없음'으로 표시한다. 이미지는 소스 커밋과 의존 태그 도장이 다른 것만 다시 빌드한다(`e2e.sh --reuse-build`가 같은 판정을 쓴다). 커밋 안 된 변경이 있으면 E2E를 거부한다: 이미지는 `git archive HEAD`로 빌드된다.

## 왜 (따른 표준과 근거)

- 변경 영향 범위에 맞춰 시험을 고르는 것(시험 선택)은 CI에서 흔한 관행이다. 단 대응표는 사람이 쓴 정적 추정이다. 근거는 e2e_steps.py의 단계 사이 상태(STATE)와 docs/E2E.md의 단계 설명이고, 표가 가리키지 않은 경계를 바뀐 코드가 건드릴 수 있다.
- 대응표의 모든 단계 이름이 e2e_steps.py에 있는지, why가 비지 않았는지, 이미지→소스 표가 build-images.sh와 같은지는 자체 시험이 확인한다(`scripts/test_verify_area.py`, Docker 불필요).
- 완료 선언의 기준은 바뀌지 않는다: 옵션 없는 전체 E2E(워크스페이스 규칙).

## 검토한 대안과 버리는 이유

- `--fast`만 쓰기: 약 2분이지만 영역과 무관하게 같은 단계를 돈다. 영역이 안 닿는 단계를 줄이지 못한다.
- 영역마다 자체 E2E 스크립트: 같은 사실(어느 단계가 어느 경계를 보는가)이 영역 리포지토리에 흩어지고 deploy 밖에서 낡는다.

## 결과

- 표가 낡으면 필요한 단계를 빼먹는다: 새 E2E 단계를 추가할 때 표를 같이 고쳐야 한다(자체 시험은 존재하지 않는 단계만 잡는다).
- model-runtime은 E2E 이미지가 `DEPLOY_MR_TAG` 태그 시점 소스라, 태그에 없는 변경은 E2E에 들어오지 않는다(도구가 알린다).

## 되돌리는 조건

단계 묶음이 자주 어긋나 전체 E2E가 계속 필요해지면 대응표를 그만두고 E2E 자체를 줄이는 쪽(병렬화)을 본다.
