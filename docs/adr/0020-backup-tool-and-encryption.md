# 0020. 백업: pg_dump 논리 백업, 서버 밖 대상 필수, age/gpg 공개키 암호화

- 상태: 채택
- 날짜: 2026-10-28

## 맥락

PostgreSQL 한 컨테이너에 데이터베이스 5개(survey, qa, ops_log, ops_failure, gate)가 있고, 파일 볼륨(gate-data 번들, models-data 모델 패키지, 레지스트리 볼륨)이 있다. 점검(head/docs/audit/deploy.md C7)에서 백업이 실제로 돌지 않았고(설정 없음), 설정이 생겨도 사본이 같은 호스트에 평문으로 남고, 복원 시험이 없고, `models-data`와 레지스트리 볼륨이 빠져 있고, 5개 DB가 한 시점이 아니었다. D88 U6이 '서버 밖 대상 필수 설정(없으면 CRIT), 암호화(age 등 표준 도구), 일일 + 정기 복원 시험'을 정했다.

## 결정

1. 데이터베이스는 `pg_dump -Fc`(논리 백업)로 데이터베이스마다 받는다. 5개를 병렬로 동시에 시작해 시간차를 줄이고 시작·끝 시각을 MANIFEST에 남긴다. 볼륨 파일 복사는 하지 않는다.
2. 백업 대상 폴더(`BACKUP_DIR`), 보관 일수, 수신자 공개키 중 하나라도 없으면 backup 잡은 "CRIT:"과 종료 코드 2로 실패하고, 운영 프로젝트의 `up.sh`는 doctor에서 멈춘다. 코드에 기본값을 두지 않는다.
3. 암호화는 파일마다, 수신자 **공개키만** 서버에 둔다. 도구는 age를 우선하고 없으면 gpg를 쓴다. 평문은 암호화에 성공한 뒤 지운다. 복호 개인키는 서버 밖에서 사람이 보관한다. 서버에서 풀 수 없다.
4. 폴더 700, 파일 600. 보관 14일(설정), 가장 최근 하나는 남긴다.
5. 파일 볼륨(gate-data, models-data, 레지스트리)은 복사 후 tar로 묶어 같은 방식으로 암호화한다.
6. 정기 복원 시험은 스케줄러 잡 `backup-restore-test`(주 1회): 시험용 키쌍으로 암호화 백업, 복호, 임시 DB 복원, 행 지문 대조, 그리고 실제 백업 파일의 해시 대조. 실제 개인키로 푸는 전체 복원 시험은 사람이 분기마다 한다.
7. 업그레이드·롤백 절차는 '적용 전 백업 성공 확인'으로 시작한다(runbook 2절, 4-5절).

## 왜 (따른 표준과 근거)

- **논리 백업(pg_dump)**: PostgreSQL 공식 문서의 표준 논리 백업이다. 데이터베이스 하나 안에서는 단일 트랜잭션 스냅샷이라 서버가 떠 있어도 일관된 사본이 나오고, 서비스(소유 계정)의 최소 권한으로 받을 수 있으며(슈퍼유저 불필요), 데이터베이스 단위로 되돌릴 수 있다. 볼륨 파일 복사는 서버가 쓰는 중에는 일관되지 않다(pg-backup.sh 머리말).
- **서버 밖 대상, 암호화, 일일, 정기 복원 시험**: D88 U6(사용자 지시 '모든 문제에 대해 가장 표준적인 방법')이 정한 것이다. 보관 14일은 D88 U4. 일일은 D85(5)의 표준값.
- **공개키 암호화**: 서버가 뚫려도 백업이 읽히지 않으려면 서버에 복호 능력이 없어야 한다(대칭키·서버 보관 개인키는 이 목적에 맞지 않는다). 그래서 수신자 공개키 방식이다. age는 D88 U6이 지명했고, 키링·신뢰 모델 없이 수신자 한 줄(공개키)만으로 쓰는 작은 도구라 서버에 두는 설정이 가장 작다(이 판단은 이 에이전트의 추론이고 비교 실험은 하지 않았다). gpg는 대부분의 배포판에 기본으로 깔려 있어 age가 없을 때의 대안으로 둔다(이 개발 호스트에는 gpg만 있어 gpg로 시험했다. age 경로는 코드만 있고 **실행해 보지 못했다**).
- **파일마다 암호화**: 스트림 하나로 묶으면 복원 시험·부분 복원에서 파일 하나만 풀 수 없다.
- **병렬 동시 시작**: PostgreSQL은 데이터베이스를 가로지르는 단일 스냅샷을 지원하지 않는다(pg_dump의 스냅샷 공유는 한 데이터베이스 안에서만 유효). 가능한 최선은 시간차를 덤프 하나가 걸리는 시간 이하로 줄이고 그 사실을 기록하는 것이다.

## 검토한 대안과 버리는 이유

- **물리 백업 + WAL 보관(PITR, pg_basebackup, pgBackRest, Barman)**: 복구 시점을 분 단위로 줄일 수 있다. 하지만 O16(허용 중단 시간·복구 시점)이 사용자 결정 전이고 WAL 보관 대상·인프라가 필요하다. 일일 논리 백업의 복구 시점은 최대 24시간이다. 버리는 이유는 '필요 없다'가 아니라 '요구가 정해지지 않았다'이다. O16이 분 단위를 요구하면 재검토한다.
- **볼륨(pg-data) 스냅샷/복사**: 일관성이 없다. 버린다.
- **암호화 없이 접근 통제(폴더 권한)만**: 사본이 서버 밖 대상으로 나가면 권한이 따라가지 않는다. 버린다.
- **서버에 대칭 비밀번호/개인키를 두는 암호화**: 서버 침해 시 백업까지 읽힌다. 버린다.
- **디스크 전체 암호화(LUKS)만**: 대상 디스크의 암호화는 별개로 유용하지만(C5, 호스트 일) 백업 파일 자체의 보호와 전송 경로를 대신하지 않는다. 대체가 아니라 병행 권고.

## 결과

- 얻는 것: 백업 없이 운영하지 않는다(설정 없으면 기동 불가), 서버 침해로 백업이 읽히지 않는다, 복원 사슬이 매주 자동으로 검증된다.
- 감수하는 것: (a) **개인키를 잃으면 백업을 못 푼다**(보관은 사람 몫). (b) 데이터베이스 사이 같은 시점이 아니다(runbook 4-2절). (c) 최대 24시간 데이터 손실(일일). (d) 서버에는 개인키가 없어 자동 복원 시험은 도구 사슬과 파일 무결성만 보증하고, 실제 키로 푸는 시험은 사람이 한다. (e) **`secrets/`(DB 암호, 비식별 salt `deid-salt` 등)는 이 백업에 들어 있지 않다.** 서버를 잃으면 비밀 폴더는 별도로 보관한 사본이 있어야 복구된다. 보관 방법은 정해지지 않았다(사용자 결정, OPEN_GAPS 후보). (f) 주 1회라는 복원 시험 주기와 분기 1회 사람 시험 주기에는 **근거 기록이 없다**(시작값). (g) 대상 폴더가 실제 '서버 밖'인지는 `backup-check.sh`가 알 수 없다(같은 디스크면 WARN).

## 되돌리는 조건

- O16이 분 단위 복구 시점을 요구하면 PITR(물리 백업 + WAL 보관)로 바꾸고 이 ADR을 대체한다.
- 병원이 다른 백업 솔루션(에이전트형, 스토리지 스냅샷)을 이미 운영하면 그것이 위 1~5를 만족하는지 확인한 뒤 대체한다.
