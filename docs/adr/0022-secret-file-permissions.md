# 0022. 비밀 파일 권한: 폴더 700, 호스트 전용 600, 컨테이너가 읽는 파일은 644

- 상태: 채택
- 날짜: 2026-10-28
- 관련: D84(비밀은 파일로), 점검 B3·F5

## 맥락

비밀은 compose `secrets:`(파일)로 `/run/secrets`에 마운트한다(D84). 점검에서 모든 파일이 644이고 계정 평문 암호가 디스크에 남으며 회전 절차가 불완전하다고 지적되었다. 목표는 0600/0400이었다.

## 결정

1. 비밀 폴더와 `tokens/`는 700.
2. **호스트에서만 쓰는 파일**(게이트웨이 계정 평문 암호·해시, 기기 토큰 원본, 컨테이너에 마운트하지 않는 클라이언트 토큰)은 **600**.
3. **컨테이너가 읽는 파일**(compose의 `secrets:`/`configs:`가 가리키는 파일, 추론 서버용 `model-runtime-tokens`·`gate-read-model-serving`·`external-inference`, 게이트웨이 설정 2개)은 **644**, 폴더 700 안에서.
4. 어느 쪽인지는 `lib.sh`의 `secret_mode`가 `compose.yaml`을 읽어 정한다. `gen-secrets.sh`는 실행할 때마다 모드를 바로잡고, `check-secret-perms.sh`(doctor --up)가 어긋남을 FAIL로 알린다.
5. 평문 계정 암호는 해시가 없을 때만 만들고, 운영에서는 `gen-secrets.sh --drop-plaintext`로 지울 수 있다(해시가 남아 로그인은 그대로, 지운 평문은 되살리지 않는다). 회전은 `rotate-account.sh`(해시만 저장)와 runbook 7절의 수동 절차. 토큰에 만료는 없다.

## 왜 (따른 표준과 근거)

- 최소 권한(파일은 소유자만)이 표준이고 3번이 그것을 못 지키는 이유는 **측정한 제약**이다: 이 호스트(Docker Engine 29.2.0, Compose 5.0.2)에서 compose의 파일 `secrets`는 호스트 소유자·모드를 그대로 마운트하고 long syntax의 `uid`/`gid`/`mode`는 적용되지 않았다. 호스트 사용자(uid 1000) 소유의 0600 파일을 `user: 10001`인 컨테이너가 읽으려 하자 읽기에 실패했다(시험으로 확인, 2026-10-28). 그래서 컨테이너가 읽는 파일을 600으로 만들면 서비스가 뜨지 못한다.
- 3번의 644는 폴더 700 안이라 호스트의 다른 사용자는 파일에 닿지 못한다. 남는 노출은 같은 사용자와 docker 그룹이다(docker 그룹은 사실상 root와 같고 어차피 모든 비밀에 닿는다).
- 평문 최소화: 해시만으로 충분한 것(Caddy 로그인)은 해시만 저장한다. bcrypt 해시는 Caddy 표준 방식(`caddy hash-password`).

## 검토한 대안과 버리는 이유

- **모든 파일 600 + 일회성 root 컨테이너로 chown 10001**: 600 소유자가 10001이 되면 호스트 사용자가 비밀을 읽거나 회전할 수 없고(docker를 거쳐야 함) 모든 스크립트가 복잡해진다. 얻는 보호는 '같은 호스트의 다른 비root 사용자'뿐인데 그것은 폴더 700이 이미 막는다. 버린다.
- **컨테이너를 호스트 uid로 실행**: 이미지 10개가 uid 10001을 전제로 만들어졌고 영역 소유다. 버린다.
- **그룹 권한(640 + gid 10001)**: 호스트 사용자가 gid 10001 그룹이 아니면 chgrp에 root가 필요하다. 버린다.
- **Docker Swarm secrets**: uid/mode를 지원하나 swarm 도입은 이 구성의 규모에 과하다(ADR 0001-compose의 Swarm 항목).
- **엔트리포인트가 시작 때 /run/secrets를 복사·chmod**: 이미지 엔트리포인트는 영역 소유라 deploy가 바꿀 수 없다.

## 추가 검토(2026-10-28): 그룹 읽기(640) + `group_add`로 644를 없앨 수 있는가

작은 격리 시험으로 확인했다(Engine 29.2.0, Compose 5.0.2). 호스트 사용자 소유·그룹 = 호스트 사용자의 주 그룹(gid 1000)인 **0640** 파일을 compose 파일 secret으로 마운트하고, `user: 10001:10001` 컨테이너에 `group_add: ["1000"]`을 주자 `id`에 groups=10001,1000이 나오고 파일을 **읽을 수 있었다**(READ_OK). 즉 이 버전에서 **된다**: chgrp(root 필요) 없이, 호스트 사용자의 주 그룹을 파일 그룹으로 쓰면 되기 때문이다. 남는 노출은 '그 그룹의 다른 호스트 사용자'(보통 개인 그룹이라 없음)로 644(모든 사용자)보다 좁다.
**적용하지 않았다**: 서비스 약 13개의 `group_add`와 `gen-secrets.sh`의 모드 결정(`secret_mode`를 640으로, 호스트 gid 변수 `SECRETS_GID=$(id -g)`)을 한꺼번에 바꿔야 하는데, 이 변경은 병합 조율 중인 공용 파일(`compose.yaml`, `gen-secrets.sh`)을 건드린다. 적용 절차: (1) `x-hardening`에 `group_add: ["${SECRETS_GID:?}"]` (job-*와 `compose.inference.yaml`도), (2) `secret_mode`가 컨테이너 읽기 파일에 640을 돌려주고 파일의 그룹이 `SECRETS_GID`인지 `check-secret-perms.sh`가 확인, (3) 다른 호스트로 옮기는 추론 서버용 파일은 그 호스트의 gid를 따로 준다. 주의: 다른 호스트·CI에서 gid가 다르면 `SECRETS_GID` 지정이 필요하다. 전체 E2E에서 확인한 뒤 적용하는 것을 권한다.

## 결과

- 얻는 것: 호스트 전용 비밀은 600, 평문 계정 암호는 운영에서 지울 수 있다, 권한 어긋남을 doctor가 잡는다, 회전 절차가 문서화됐다.
- 감수하는 것: 컨테이너가 읽는 비밀 파일이 644다(폴더 700 의존). 같은 사용자·docker 그룹은 읽을 수 있다. `gateway-devices.caddy`는 기기 토큰을 평문으로 담고 644다(Caddy가 읽어야 한다). 해시 생성(`caddy hash-password`) 때 암호는 `docker run -i`의 **표준 입력**으로 전달되어 프로세스 인자에 나타나지 않는다(정정 2026-10-29: 이 항목은 원래 "docker run 인자로 보인다"고 적었으나 코드는 점검 L6 이후 표준 입력을 쓴다. `scripts/test-hash-password-argv.sh`가 가짜 docker로 인자와 표준 입력을 기록해 확인한다). 남는 노출은 호스트 셸 변수와 `rotate-account.sh`가 표준 출력으로 내는 새 암호 한 줄이다. **토큰 만료·회전 주기는 근거 기록이 없다**(수동, 주기 미정). 계정은 OIDC 도입 전의 임시 방식이다(D85(3)).

## 되돌리는 조건

- Compose가 파일 secrets의 `uid`/`mode`를 적용하는 버전으로 올라가면(올린 뒤 같은 시험을 다시 한다) 3번을 400/600으로 바꾼다.
- OIDC 도입으로 게이트웨이 계정 해시가 없어지면 5번의 계정 부분이 사라진다.

## 후속 판단(2026-10-28, OPEN_GAPS L02): 640 + group_add를 지금 적용하지 않는다

격리 시험(위)은 통과했지만 이 저장소의 실제 구성에 적용하는 데는 아래가 남았고, 이를 검증하는 수단이 이번 작업에서 허락되지 않아(전체 E2E는 최종 관문 1회만) 적용하지 않았다. 적용하면 확인하지 못한 채 서비스가 비밀을 못 읽는 위험을 만든다.
- 바꿀 곳: `x-hardening`을 쓰는 서비스 10개(postgres는 uid 999)와 hardening 앵커를 쓰지 않는 `job-*` 4개, `compose.inference.yaml`; `lib.sh`의 `secret_mode`, `gen-secrets.sh`, `check-secret-perms.sh`와 그 자체 시험, `SECRETS_GID`를 쓰는 모든 호출(up.sh, E2E, 백업 시험, 단독 시험).
- 이식성: gid는 호스트마다 다르다. 다른 호스트(gpu-dev, CI, 운영)에서 `SECRETS_GID` 없이 띄우면 비밀을 못 읽는다. 외부 추론 서버용 파일은 그 호스트의 gid를 따로 줘야 한다.
- 검증 방법(허락되면): `gen-secrets.sh` 후 `check-secret-perms.sh`, `up.sh`에서 모든 서비스 healthy, `check-containers.sh`, 단독 단계(`check-standalone.sh`), 그리고 최종 관문의 전체 E2E 1회(백업·복구 포함). 서비스가 비밀을 읽지 못하면 healthy에서 드러난다.
- 이득: 644(같은 호스트의 모든 사용자)에서 640(파일 그룹 구성원)으로 좁아지는 것. 폴더가 700이라 호스트의 다른 사용자는 어차피 닿지 못하므로 증분 이득은 같은 사용자/그룹 범위 안이다. 이 이득이 위 변경 범위를 정당화하는지는 사용자 판단이다(미정).
