# 0030. E2E: 선행 실패는 SKIP으로 센다, 단계 입력은 선언하고 해시로 기록한다, 전체 E2E는 최종 관문으로 남긴다

- 상태: 채택(--changed-only는 구현만 했고 기본 동작은 바뀌지 않음. 어떤 단계도 단독 실행이 증명되지 않았다)
- 날짜: 2026-10-28

## 맥락

`e2e.sh`는 준비 단계 밖에서는 FAIL이 나도 끝까지 돌았고, 선행 항목이 실패해도 그에 의존하는 뒤 항목을 돌렸다. 한 번의 실행에서 "새 버전 빌드" 하나가 깨지면 "새 잠금으로 적용"과 "롤백"도 FAIL이 되어 결함 1개가 FAIL 3개로 보였다(실제 기록: E2E_RESULTS.md의 120 PASS / 3 FAIL 행). 또 단계들은 하나의 스택 상태(e2e_steps.py의 STATE, 실행 중 컨테이너)를 이어 쓰는 사슬이라 한 단계만 고쳐도 전체를 다시 돌려야 했다. 전체는 약 8분이다(ADR 0014).

## 결정

1. 입력 선언: `scripts/e2e_plan.py`의 `STEP_DECLS`(e2e_steps.py의 단계)와 `SECTION_DECLS`(e2e.sh의 구간)가 단계마다 `repos`(결과를 좌우하는 소스 리포 커밋), `deps`(상태를 의존하는 앞 단계, 없으면 `()`), `why`(근거 코드 위치), `solo`(단독 실행 증명 여부)를 선언한다. 근거를 코드에서 읽지 못한 단계(5a, 5u, demo류)는 `deps=미확인`이다. 자체 시험이 STEPS 이름과 선언의 일치, 순환, 빈 근거, 실행 순서상 뒤에 있는 deps를 검출한다. 선언이 없는 단계가 있으면 e2e_steps.py가 시작하지 않는다.
2. SKIP: 선행(확인된 deps)이 FAIL 또는 SKIP이면 의존 항목은 돌리지 않고 `SKIP(선행 실패: 항목명)`으로 표시한다. 뿌리 항목명을 전이해 남긴다. 집계는 PASS/FAIL/SKIP을 따로 세고 종료 코드는 FAIL만 본다. e2e.sh는 같은 규칙을 `chk_dep`와 `NEED` 배열로 구현한다(예: 백업이 실패하면 볼륨 삭제도 하지 않는다). E2E_RESULTS.md는 표 칸을 바꾸지 않고(옛 행 호환) SKIP이 있을 때만 출처 칸에 `SKIP n개`를 적는다.
3. `--fail-fast`: 첫 FAIL에서 요약을 내고 중단한다. 정본에는 기록하지 않는다.
4. 해시 기록과 `--changed-only`: 단계마다 (선언한 리포의 HEAD 커밋 + 추적 파일 변경 해시, 단계 함수와 그것이 부르는 최상위 함수의 소스 해시, deps)를 해시해 `deploy/state/e2e-last-pass.json`(state/는 .gitignore, 리포 밖)에 마지막 PASS 때의 값으로 적는다. `--changed-only`는 해시가 바뀐 단계, 그에 의존하는 단계, `solo`가 증명되지 않았거나 deps가 미확인인 단계를 고르고, 스냅샷이 없어 상태를 재구성해야 하므로 고른 단계의 상류도 같이 돌린다. 기본 동작은 그대로이고 정본에 기록하지 않는다.
5. 전체 E2E(옵션 없음)는 인도 전 최종 관문으로 남긴다.

## 왜 (따른 표준과 근거)

- SKIP: 단위 시험 도구가 선행 실패 뒤 항목을 skip으로 보고하는 관행(pytest의 `skip`/`dependency` 계열, xUnit의 Skipped 구분)을 따랐다. 실패와 "돌리지 못함"을 섞으면 결함 개수를 잘못 읽는다. 연쇄 FAIL은 원인 하나를 가리는 잡음이었다.
- 해시: 빌드 시스템이 입력이 같으면 결과를 재사용하는 방식(Make의 타임스탬프보다 내용 해시를 쓰는 Bazel/Nix류)에서 가져왔다. 시계가 아니라 내용을 보므로 브랜치를 오가도 틀리지 않는다.
- 전체 E2E를 남기는 이유: 출하되는 것은 서비스들의 조합이다. 단계 하나가 어제 PASS였어도 이웃 영역의 새 커밋, 이미지, 설정이 조합을 바꿨을 수 있다. 단계 선언이 놓친 경계는 전체에서만 드러난다(ADR 0014이 말한 정적 대응표의 한계와 같다).

## 검토한 대안과 버리는 이유

- 연쇄 FAIL을 그대로 두기: 개수가 결함 수가 아니게 된다. 버림.
- 의존을 자동 추론: STATE 키 접근은 읽을 수 있으나 실행 중 스택(컨테이너 상태)에 대한 의존은 코드에서 안정적으로 읽히지 않는다. 선언 + 근거 + 미확인 표시를 택했다.
- 표 칸 추가(SKIP 열): 모든 옛 행과 파서를 고쳐야 한다. 출처 칸 표기로 시작한다.
- 스택 스냅샷으로 단계를 독립으로 만들기: 컨테이너·볼륨 스냅샷 방식을 정하지 않았고 측정하지 않았다. 미정.

## 결과

- 얻는 것: 결함 1개는 FAIL 1개로 보인다. 개발 중 `--fail-fast`로 첫 결함에서 멈춘다. 입력이 안 바뀐 단계를 구별할 기록이 생긴다.
- 감수하는 것: 스냅샷이 없어 상태 의존 단계를 독립으로 만들 수 없다. 그래서 `--changed-only`는 상류까지 다시 돌린다(5p만 바뀌어도 1~4를 돈다). 어떤 단계도 아직 `solo`가 증명되지 않아 지금은 `--changed-only`가 모든 단계를 고른다(=전체와 같다). 증명이 쌓여야 줄어든다.
- 해시 기록은 낡은 결과를 재사용할 위험이 있다: 해시가 보지 않는 입력(모듈 상수, 픽스처 파일, 선언하지 않은 리포, 호스트 환경, Docker 버전)이 바뀌어도 "변경 없음"으로 읽힌다. `deps` 선언이 틀리면 SKIP이 빠지거나 과하다. 그래서 기록은 선택에만 쓰고 합격 판정에는 쓰지 않는다.
- SKIP은 "돌리지 못함"이지 합격이 아니다. SKIP이 있으면 선행 결함을 고친 뒤 다시 돌려야 한다.

## 되돌리는 조건

선언이 자주 틀려 SKIP이 진짜 결함을 가리면 SKIP 전파를 끈다(해당 deps를 미확인으로). 전체 E2E가 충분히 빨라지면(측정 필요) 해시 기록과 `--changed-only`를 없앤다.
