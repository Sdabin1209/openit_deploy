# 0031. 서비스 사이 내부 TLS를 쓰지 않는다: 범위는 compose 내부 네트워크 한정 (OPEN_GAPS L05)

- 상태: 채택(범위 한정 조건부)
- 날짜: 2026-10-28

## 맥락

사용자 쪽 TLS는 gateway가 끝낸다(ADR 0005: HTTPS 필수, 내부 CA). gateway 뒤 서비스 사이 호출(survey-service -> release-gate 등, `boundary-contracts/HTTP.md`)과 서비스 -> PostgreSQL 연결은 평문 HTTP/TCP다. 이를 명시한 결정 기록이 없어 "내부는 암호화하지 않았다"가 암묵으로 남아 있었다.

## 결정

compose 프로젝트의 내부 네트워크 안에서는 서비스 사이 TLS를 쓰지 않는다. 이 결정은 그 범위로 한정한다: 호출자와 서버가 같은 Docker 호스트의 같은 compose 프로젝트에 있고, 호출 경로마다 전용 네트워크가 있다(`compose.yaml`의 networks, E2E의 도달·차단 검사가 확인한다). 호스트 밖으로 나가는 호출은 이 결정의 범위 밖이며 TLS가 필요하다: 외부에 둔 추론 서버(`compose.external-inference.yaml`), 호스트 밖 PostgreSQL, 다른 호스트로 나눈 서비스.

## 왜

- 신뢰 경계: 위협 모델이 "내부 네트워크 밖의 도청"이면 경계는 gateway 하나다. 같은 호스트의 bridge 네트워크는 호스트 밖으로 패킷이 나가지 않는다. 이웃 네트워크 접근은 E2E가 차단을 확인한다(도달·차단 항목).
- 서비스별 인증서를 배포·회전하는 운영 부담(내부 CA, 만료, 컨테이너마다 신뢰 저장소)이 이 규모에서 위험을 줄이는 값보다 크다고 판단했다. 이 판단은 측정한 것이 아니라 설계 판단이다.
- 호출은 이미 서비스별 토큰으로 인증한다(D84). TLS가 없어도 위조 호출은 막힌다. 막지 못하는 것은 도청이다.

## 검토한 대안과 버리는 이유

- 서비스 mesh/mTLS(sidecar): 컨테이너와 설정이 크게 늘고 공급망이 넓어진다. 지금 규모에 비례하지 않는다.
- 서비스마다 Caddy 앞단: 같은 이유로 인증서 운영이 서비스 수만큼 늘어난다.

## 결과

- 얻는 것: 구성이 단순하고 인증서 만료로 서비스 사이가 끊기지 않는다.
- 감수하는 위험: 호스트의 root/docker 그룹 사용자나 같은 네트워크에 붙은 침해된 컨테이너는 서비스 사이 트래픽(토큰, 문진 응답)을 볼 수 있다. DB 연결도 평문이다. 호스트가 침해되면 TLS가 있어도 비밀 파일에 닿으므로 증분 이득은 제한적이다(ADR 0022의 docker 그룹 서술과 같은 논리).
- 확인하지 못한 것: 컨테이너 사이 패킷이 실제로 호스트 밖으로 나가지 않는다는 것을 패킷 수준으로 보지는 않았다. 네트워크 구성(internal 네트워크, 게시 포트 없음)과 E2E 차단 검사에 근거한다.

## 되돌리는 조건

(1) 서비스 일부를 다른 호스트로 나눌 때(그 호출만 먼저 TLS), (2) 병원 보안 심사가 내부 암호화를 요구할 때, (3) 같은 호스트에 신뢰할 수 없는 다른 워크로드가 올라올 때, (4) 컨테이너 침해를 위협 모델에 넣게 될 때. 새 ADR이 이 ADR을 `Supersedes`한다.
