# 0044. 백업 보관 기간은 운영 데이터 보존 기간 중 가장 짧은 값 이하로 한다

- 상태: 채택
- 날짜: 2026-10-30

## 맥락

운영 DB는 보존 기간이 지난 데이터를 지운다(survey 세션 90일, ops-feedback 원본 Trace 30일·사례 180일·지표 365일, question-authoring 초안·원본 30일). 백업(restic, ADR 0038)은 DB 덤프를 스냅샷으로 `BACKUP_RETENTION_DAYS` 동안 보관한다. 백업 보관이 데이터 보존보다 길면 운영에서 지운 데이터가 백업에 남아 보존 정책이 우회된다(OPEN_GAPS U30). release-gate는 보존 값이 deploy 설정에 없다(영역 기본값, 이 ADR은 확인하지 못했다).

## 결정

`BACKUP_RETENTION_DAYS` ≤ deploy가 설정하는 운영 데이터 보존 일수의 **최솟값**(지금 30일: `OPS_RAW_RETENTION_DAYS`, `QA_DRAFT_RETENTION_DAYS`, `QA_SOURCE_RETENTION_DAYS`, 잡 설정 `retention.raw_days`)이어야 한다. `config/backup.env.example`의 값은 D88 U4의 일일 백업 기본 14일을 유지한다(30 이하라서 바꾸지 않는다). 강제 수단 둘:
- `scripts/retention_check.py`: 설정(`config/*.env`의 `*_RETENTION_DAYS`, `ops-feedback-job.yaml`의 `retention.*_days`, `compose.yaml` environment의 숫자 값)에서 가장 짧은 값을 읽어 비교한다. 값을 하나도 못 읽으면 통과가 아니라 실패(종료 2).
- `backup-check.sh`(doctor --up, init이 부른다)가 이 점검을 불러 어기면 CRIT로 거부한다. 정적 시험 `test_retention_check.py`는 self-checks.list에 있다.

## 왜

- 값은 **측정이 아니라 제약에서 나왔다**: 백업이 운영 보존 정책을 우회하지 않아야 한다는 요구에서 "백업 보관 ≤ 데이터 보존"이 나온다. 14일은 일일 백업 기준의 기본값이고 이 제약 안에 든다. 병원 규정으로 값이 바뀌면 점검이 어긋남을 알려 준다.
- 정확한 한계: 보존 기간 R이 지나 지운 행이 지우기 직전 찍힌 스냅샷에 남으므로, 지운 데이터는 백업에 최대 K(백업 보관)일 더 남는다. K ≤ R이면 지운 뒤 백업에 남는 기간이 데이터가 DB에 있던 기간을 넘지 않는다(총 수명 ≤ 2R). 지운 즉시 백업에서도 사라지게 하려면 K=0에 가까워야 하고 복구 가능 기간과 맞바꾸게 된다. 이 ADR은 그 맞바꿈의 상한만 정한다(더 엄격한 값은 병원 규정이 정한다).
- 한 곳에서 읽는다: 보존 값을 이 ADR이나 점검에 다시 적지 않고 설정 파일에서 읽는다(값이 둘이 되지 않게).

## 검토한 대안

- 백업 보관을 보존 값과 같게(K=R): 복구 가능 기간이 길어지지만 지운 데이터가 최대 R일 더 남는다. 상한 규칙(≤)은 이것을 허용하되 강제하지 않는다.
- 문서로만 경고: 설정이 바뀔 때 놓친다(실제로 이 공백이 대장에 있었다).
- 서버의 DB 보존 잡이 백업도 지우게 함: 백업은 서버가 지우지 못하는 append-only 저장소다(D112, ADR 0038). 되지 않는다.

## 결과

얻는 것: 보존이 더 짧아지거나 백업 보관이 길어지면 백업 점검과 정적 시험이 막는다. 감수하는 것: 점검은 deploy 설정에 적힌 값만 본다(release-gate 보존 값은 영역 기본값이라 보지 못한다), 운영 `backup.env`는 리포에 없어 예시 파일과 `backup-check.sh`가 각각 본다. 측정한 것은 없다.

## 되돌리는 조건

병원 규정이 지운 데이터의 백업 잔존을 보존보다 길게 허용하면(예: 법정 백업 보관 기간) 이 ADR을 그 규정으로 대체한다.
