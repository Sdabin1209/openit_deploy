# 0050. E2E 는 샌드박스로 돈다: 제품에는 시험용 문이 없다

- 상태: 채택 (사용자 지시 "시험은 샌드박스 방식으로", 헤드 전달 wo-441, 2026-11-01)

## 맥락

E2E 는 운영 `compose.yaml` 위에 `compose.test.yaml` 을 덮어 제품 구성에 시험용 문을 냈다: 내부 서비스 7개(survey-service, question-authoring, ops-feedback-ingest, release-gate, model-serving, model-registry, dataset-store)의 호스트 포트, 서비스마다 시험 네트워크, 가짜 백엔드 플래그(`MODEL_RUNTIME_ALLOW_FAKE`). 드라이버(`e2e_steps.py`)는 그 문으로 들어갔다(release-gate 내부 포트 직접 호출 18회, 게이트웨이 경유 6회).

결과: "운영 입구(게이트웨이)만으로 되는가" 같은 경계 요구가 시험으로 증명되지 않았다. 실제 결함(D72: 다른 호스트의 추론 서버가 release-gate 에 닿을 운영 경로가 제품에 없었다)이 E2E 통과 뒤에야 드러났다. E2E 가 통과해도 제품이 시험용 문에 기대어 도는지 알 수 없었다.

## 결정

- **제품 = `compose.yaml`(+ 운영 overlay `compose.external-inference.yaml`)**. `compose.test.yaml` 을 지운다. 제품 compose·config 에는 시험을 위한 줄이 없다.
- 드라이버는 **호스트(운영자 PC 역할)에서** 돌고 접근은 셋뿐이다: (a) 게이트웨이 호스트 포트(HTTPS, 게이트웨이 CA 만 신뢰; 사람 계정·기기 토큰·추론 기계 토큰), (b) `docker compose -p <P> exec / logs / run --rm <job-*>`(제품 네트워크 안에서 제품의 컨테이너·잡을 실행), (c) 다른 호스트 역할의 컨테이너 = `compose.inference.yaml` 을 **별도 프로젝트**(`<P>-inf`)로 띄운 추론 서버(가짜 백엔드 변수는 그 쪽 env 만, 호스트 포트 게시는 그 컨테이너 자신의 것).
- 접근 계층은 `scripts/e2e_sandbox.py` 한 곳이다(`gw_request`, `gw_client`, `exec_in`, `exec_py`, `run_job`, `readyz`, `psql`, `logs`, `inference_url`). 단계 코드는 호스트에서 내부 서비스 포트를 부르지 않는다.
- 시험 가속 값은 **제품이 이미 가진 운영 설정 변수의 값**만 `test/sandbox.env` 로 넘긴다(`GATE_POLL_SECONDS`). 새 변수·새 문을 만들지 않는다.
- 끝 조건: 단계 코드에 내부 포트 직접 호출 0건, 제품 compose 에 시험용 문 0건. 정적 점검 `scripts/test_compose_no_test_doors.py`(`check-all.sh` 에 연결)와 e2e.sh 의 실행 중 컨테이너 점검(호스트 포트를 게시한 제품 컨테이너는 gateway 뿐)이 본다.
- 기동 순서: 추론 서버 -> 제품(`up.sh`, 외부 추론 모드) -> 게이트웨이 TLS 포트·CA 를 읽어 추론 서버를 그 입구로 다시 설정 -> 바뀐 추론 서버 주소를 제품에 다시 알림. 순서의 이유는 `scripts/e2e.sh` 주석.

## 왜

- 표준·원칙: 시험은 제품이 배포되는 모양 그대로를 대상으로 하고 시험 대상 밖에서 들어가야 한다(블랙박스 시험, 시험용 훅이 제품에 없어야 시험이 제품을 증명한다). 구조 규칙 6개(D104)도 같은 방향이다: 컴포넌트는 서로의 내부(포트·이웃 파일 구조)에 기대지 않고 스키마·입구로만 만난다.
- D72 결함이 증거다: 다른 호스트 추론 서버의 입구 경로가 없다는 사실이 시험용 문 때문에 가려졌다. 같은 모양의 결함이 다른 경계에도 있을 수 있다.

## 검토한 대안과 버리는 이유

- **덮어쓰기 유지**(`compose.test.yaml` 을 그대로 두고 문만 줄인다): 문이 한 개라도 남으면 그 문으로 닿는 경계는 증명되지 않는다. 어느 문이 필요한지 판단이 쌓이는 만큼 제품과 시험이 다시 갈라진다. 버린다.
- **시험용 이미지 변형**(시험 코드를 이미지에 넣는다): 제품 이미지와 시험 이미지가 달라진다. digest 로 되돌리는 코드 축(D07)의 의미가 사라진다. 버린다.
- **추론 서버 포트를 미리 골라 재생성을 없앤다**: 빈 포트 선택은 경쟁이 있고 호스트 포트는 Docker 가 배정한다는 규칙과 어긋난다. 재생성 한 번의 비용(수 초)이 작다. 버린다.

## 결과

- 얻는 것: E2E 가 통과하면 운영 입구와 운영 모드 overlay 만으로 제품이 돈다는 뜻이 된다. 시험용 문이 제품에 들어오면 정적 점검이 실패한다.
- 감수하는 것: 단계가 게이트웨이·exec 로 돌아 느려질 수 있다(**측정하지 않았다**). 게이트웨이로 노출되지 않은 내부 경로를 직접 부르던 단계는 게이트웨이 경로·`exec_py`(컨테이너 안의 클라이언트)로 다시 써야 한다. 복구 검증(`link_restore_verify`)처럼 내부 포트를 받는 컴포넌트는 별도 전환이 필요하다. 감시 스택(compose.monitoring.yaml)의 호스트 포트 2개는 결정되지 않아 정적 점검이 예외로 출력한다.

## 되돌리는 조건

샌드박스로는 증명할 수 없는 요구가 생기고(예: 내부 서비스 단독 계약 시험) 그것을 영역 자체 시험(각 영역의 메모리 구현)으로 옮길 수 없을 때. 그때도 제품 compose 에 문을 내지 않고 별도의 시험 전용 프로젝트를 둔다.
