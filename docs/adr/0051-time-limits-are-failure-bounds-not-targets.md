# 0051. 시간 상한은 실패 판정 상한이다: 목표(SLO)와 분리하고 표준 기준으로 잡는다

- 상태: 채택 (사용자 결정 D125, 2026-11-02)
- Supersedes: 0048 의 값과 0047 의 값(사슬 규칙 "바깥이 안쪽보다 길다"는 유지)
- 날짜: 2026-11-02

## 맥락

환자 턴 응답 2초는 목표가 맞다. 그런데 ADR 0047·0048 은 이 목표에서 거꾸로 상한을 정했다(extract 3.0·respond 5.0·턴 9·gateway 1+9.5·키오스크 12; 사람 화면 gateway 13/10·서버 12/9). 목표를 그대로 실패 판정으로 쓴 것이다. 실측(H4, 2026-11-02): 첫 환자 턴의 extract 가 Triton JIT 컴파일 때문에 3.0초를 넘겨 턴이 실패했다. 사용자 결정: "2~3초 넘었다고 모든 처리를 실패시키는 건 비즈니스 로직상 맞지 않다. 표준 기준으로 상한을 바꿔라."

## 결정

계약 `boundary-contracts/CONVENTIONS.md` "시간 상한 사슬" 표와 같은 값을 쓴다.

환자·직원 경로: 키오스크 대기 60s > gateway 연결 1s + 응답 헤더 55s > survey 턴 총 마감 50s > survey 클라이언트 extract 21s·respond 26s > model-runtime extract 20s·respond 25s.

사람 화면(gateway 연결 1s + 응답 헤더 / 서버 전체 마감 / 화면 대기): release-gate 180s / 170s / 190s, question-authoring 120s / 110s / 130s, ops-feedback 60s / 55s / 70s. 서버 마감과 화면 대기는 각 영역이 바꾼다. 정적 화면(admin-console) 프록시 10s 는 그대로다.

목표(SLO) 환자 턴 2초(p95)는 지표와 경보로만 본다(`config/prometheus/` 규칙, 요청을 끊는 값이 아니다).

## 왜

- 프록시·부하분산기의 표준 읽기/유휴 상한은 60초다(nginx `proxy_read_timeout` 기본 60s, AWS ALB idle timeout 기본 60s). 키오스크 대기와 ops-feedback 경로를 이 표준에 맞췄다.
- 화면 응답 지침(Nielsen): 1초를 넘으면 진행 표시, 10초를 넘으면 안내 문구. 상한 전에도 사용자는 "생각 중" 표시를 본다(kiosk-frontend 영역의 몫).
- 사람 화면의 값은 측정된 최악값 위의 여유다: 승인 최악 128초(D120 계기) -> 180s, 자료 올리기 최악 62초 -> 120s, 검토 최악 11초 -> 프록시 표준 60s. 이 측정은 한 환경의 것이며 다른 환경에서 다시 재지 않았다.
- 모델 두 번 호출의 상한 합(20 + 25 = 45s)이 턴 마감 50s 보다 짧다. survey 클라이언트 상한은 서버 상한보다 1초 길어 서버가 먼저 503 을 낸다.

## 검토한 대안

- 값만 조금 올린다(예: extract 3 -> 5): 버린다. 같은 결함(목표에서 상한을 거꾸로 정함)을 남기고, 다음 JIT·콜드 스타트·부하 지연에서 다시 실패한다.
- 상한을 없앤다: 버린다. 무응답 상류에 요청이 무한정 매달리고 사슬 규칙의 근거(분류된 실패의 전달)가 사라진다.

## 결과

얻는 것: 첫 호출 JIT 같은 정상 지연에 턴이 실패하지 않는다. 감수하는 것: 진짜 장애(상류 무응답)의 감지가 최대 56초(사람 화면은 최대 181초)로 느려진다. 그 감지는 이제 지표·경보가 맡는다. E2E 5w 는 무응답 상류에서 55초를, 5u 는 180초와 60초를 기다리므로 단계가 길어진다. 연결 거부는 dial 단계에서 끝나 1초대 503 으로 그대로다(5q).

## 되돌리는 조건

사용자가 상한 값을 바꾸면(계약 CONVENTIONS 시간표 개정) 이 ADR 을 새 ADR 이 대체한다. 측정으로 정상 지연이 이 상한에 가까워지면 같은 방식으로 다시 정한다.
