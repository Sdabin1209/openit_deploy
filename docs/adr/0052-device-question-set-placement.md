# 0052. 기기에 문진표를 배치하는 방식: 기기 설정 파일의 선택 칸 하나

- 상태: 채택 (사용자 결정 2026-11-03: 문진표 여러 개가 함께 활성, 기기 배치가 기본)
- 날짜: 2026-11-03

## 맥락

계약 3.3.0 부터 활성 릴리스는 문진표(문항 세트)를 여러 개 담고, 세션 시작 때 `question_set_id` 로 하나를 고른다(둘 이상이면 필수). 기본은 기기에 배치된 문진표이고, 배치가 없으면 키오스크 첫 화면에서 고른다. 배치를 어디에 두고 누가 쓰는가가 문제다.

## 결정

배치는 기기 설정 파일 `secrets/kiosk-config/<기기 ID>.json` 의 선택 칸 `question_set_id`(계약 `DeviceConfig`, 패턴 `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`)에만 둔다. 쓰는 곳은 `scripts/kiosk-add-device.sh`(`add --question-set`, `place`, `from-list` 의 둘째 칸) 하나다. 쓰기 전에 `DeviceConfig` 로 검증하고(R7), 기동 전 점검 `check_config_contracts.py` 가 폴더의 모든 기기 설정을 같은 스키마로 다시 검증한다. 토큰 회전과 배치 없는 `add` 는 기존 배치를 유지한다. 게이트웨이와 survey-service 는 배치를 모른다.

## 왜

- 계약이 이미 `DeviceConfig.question_set_id` 와 `KioskStartFragment.question_set_id` 를 정의했다. 그 파일을 deploy 가 만든다(`DeviceConfig` 의 쓰는 쪽). 새 형식을 만들지 않고 계약 칸을 쓴다(구조 규칙 6: 영역 간 스키마는 헤드 책임).
- 구조 규칙 1·4: survey-service 는 기기와 문진표의 대응을 알 필요가 없다. 요청 본문의 `question_set_id` 만 보면 된다. 키오스크도 자기 설정과 목록 응답만 본다.
- 기기 토큰과 같은 산출물에 두면 기기당 파일 하나로 운영자가 이미 하는 일(기기 설정 전달)에 얹힌다. 배치를 바꿔도 비밀 목록이 아니라서 게이트웨이를 재시작하지 않는다.
- 정본이 한 곳이다(파일). 목록 파일(`config/kiosk-devices.conf`)은 입력일 뿐이고 `place` 가 나중에 바꾸므로 둘이 어긋날 수 있으나, 파일이 항상 나중에 쓴 값을 갖는다.

## 검토한 대안과 버리는 이유

- 게이트웨이 설정(Caddy)에 기기 토큰별 문진표를 두고 헤더로 붙인다: 게이트웨이가 문진표 개념을 알게 되고(규칙 1), 바꿀 때마다 재시작해야 한다.
- survey-service 에 기기별 기본 문진표 표를 둔다: 영역 간 새 입력이라 계약 변경이 필요하고, 키오스크 첫 화면 선택과 두 군데서 정해진다.
- 시작 URL 조각만 쓴다: 기기마다 사람이 URL 을 열어야 해서 고정 배치(로비 기기)에 맞지 않는다. 조각은 계약대로 설정보다 먼저인 한 번의 덮어쓰기로 남긴다(데모 `--question-set`).

## 결과

- 얻는 것: 서버 무변경, 배치 변경에 재시작 불필요, 배치가 계약으로 검증됨.
- 감수하는 것: 배치를 바꾸면 새 설정 파일을 기기에 다시 전해야 한다. 배치한 문진표가 활성 릴리스에 없으면 시작이 400(`UNKNOWN_QUESTION_SET`)이다. 키오스크가 이 파일을 읽어 본문에 싣는 구현은 kiosk-frontend 영역의 일이다(E2E 5k 는 그 앱의 동작을 스크립트로 흉내 낸다: 확인한 것은 서버 쪽 계약뿐).

## 되돌리는 조건

계약이 배치를 서버 쪽 상태(기기별 기본 문진표)로 옮기면 이 ADR 을 대체한다.
