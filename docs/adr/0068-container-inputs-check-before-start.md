# 0068 기동 전에 compose 주입을 이미지 주입 선언과 대조한다

- 상태: 채택(2026-11-06)

## 맥락
deploy 는 영역 이미지를 읽기 전용 루트·cap_drop ALL 로 띄우고 비밀·설정 파일·쓰기 마운트를 준다. 무엇을 어디에 어떤 권한으로 줘야 하는지는 문장 규칙뿐이었다. 2026-11-06 E2E 기동이 DB 비밀 읽기, TLS 사본 경로, 잡 argv 로 실패했고, 정적 대조로는 감시 스택이 /tmp 를 받지 못하는 결함이 나왔다. 모두 이미지의 필요와 deploy 의 주입이 어긋난 것이었다.

## 결정
계약 3.5.0 `ContainerInputs`(이미지 라벨 `io.openit.inputs`)를 정본으로, 컴포넌트 `container_inputs_check` 가 서비스마다 규칙 I1~I10(읽기 전용, 권한, sysctls, 사용자·진입점 덮어쓰기 금지, 묶음 존재, 선언 파일 주입, 선언 밖 파일 금지, 쓰기 경로·쓰는 사용자, 선언 밖 쓰기 마운트 금지, 비밀 그룹)을 대조한다. `up.sh` 는 잡 프로필까지 포함한 `docker compose config` 로 대조하고 어긋나면 기동하지 않는다. E2E 의 추론 서버 기동과 운영 추론 호스트 절차(docs/RUN.md)도 같은 대조를 먼저 한다.

## 왜
- 실행해야 드러나던 결함을 기동 전에, 컨테이너를 띄우지 않고 잡는다(사용자 지시: 코드로 먼저 확인).
- 선언은 이미지를 만드는 영역이 내고(라벨), deploy 는 이웃 리포 구조를 읽지 않는다(구조 규칙 1). 라벨로 오는 선언은 계약 validator 로 검증한 뒤 쓴다(R7).
- 표준: compose 해석 결과(`docker compose config --format json`)를 그대로 입력으로 쓴다. 상대 secrets target 은 /run/secrets 아래, configs 기본 target 은 /<이름>(compose 명세).

## 검토한 대안과 버리는 이유
- E2E 로만 확인: 기동 실패가 한 번에 하나씩 드러나 E2E 를 여러 번 돌렸다(부품 부하·시간).
- deploy 가 이미지를 실행해 사용자·경로를 알아내기: 실행에 기대고, 선언(약속)이 아니라 관찰이라 바뀌어도 모른다.

## 결과
- 얻는 것: 주입과 선언이 다르면 기동 전에 서비스·규칙·경로로 알린다. 선언 밖 비밀·마운트가 남지 않는다(외부 추론 덧씌움의 남는 토큰을 같은 이름 덮어쓰기로 고침).
- 감수하는 것: 영역이 주입을 바꾸면 선언과 deploy compose 를 같이 바꿔야 한다(그것이 목적이다).

## 되돌리는 조건
배치가 compose 밖으로 옮겨 가면 같은 대조를 그 배치 형식 입력으로 다시 만든다.

## 검토 보완(2026-11-06)

- 서버와 잡은 각자의 env_schema 및 CommonEnv를 검증한다. 서버 전용 필수 조건을 잡에 적용하지 않는다.
- JobsDeclaration이 소유하는 argv/config는 ContainerInputs와 조합해서 검사한다. 같은 설정 경로를 선언 두 곳에 복제하지 않는다.
- 생성 → 최종 compose 검사 → 같은 생성물 기동 순서다. 검사 뒤 잡 정의를 다시 만들지 않는다.
- 명시된 tmpfs uid/gid/mode, 파일 bind와 폴더 구분, 서비스 명령·빈 진입점 덮어쓰기 및 잡 argv 일치를 검사한다. tmpfs 옵션이 생략된 경로의 권한은 이미지 실측 시험이 필요하며 1777로 추정하지 않는다.
- 역할에 선언된 JSON 설정 파일은 실제 override 마운트에서 읽어 그 내용 스키마를 적용한다. 잡 설정은 생성된 x-openit-job-input을 기존 설정 계약 관문이 검사한다.
